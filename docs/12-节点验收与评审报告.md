### 评审发现(按严重度)

**🔴 P0-1|计费账本落在易失存储。** SQLite 在 Render 免费档容器文件系统内,**每次重新部署数据清零**。
测试期无妨;但真实付款进来后,一次部署就会抹掉客户已购额度与订单史——**收真钱前必须外置**
(Render 付费持久盘,或免费档 PostgreSQL 如 Neon/Supabase,store 层已抽象、迁移量可控)。
**裁定:支付宝正式上线收款前为硬前置,立为 gate 后首个平台事项。**

**🟡 P1-1|无速率限制与登录失败锁定**(docs/05 已知,M2-G1)。当前公网实例经手真实口令,风险窗口存在但可控(强口令+低知名度)。
**🟡 P1-2|支付宝密钥对经手本会话环境**(生成时已声明);上线稳定后委托人自助轮换,流程已写入使用说明。
**🟡 P1-3|实验种子方差大**(极差最高 21.7 分):四种子补测执行中,C2 报告以均值±标准差呈现。
**⚪ P2|**DJ 引擎适配器未实测(需装 py-data-juicer 的环境);GitBook 站未连接(委托人侧);微信支付适配器未联调(无商户号)。

## 四、评审结论

1. **架构层面**:五层设计(docs/02)中 L1–L3 与 L5 的最小实现全部落地且有测试与真机证据;
   L4(归因/配方注册)尚在实验基建形态——符合"gate 前不平台化"的纪律。
2. **最大隐患已定位**:P0-1(账本易失)。幸运的是发现于收款闭环打通之前;整改路径明确且便宜。
3. **实验纪律经受了一次实战检验**:单种子强结论被复验修正——评审确认"复验+均值±方差"
   成为 C2 的呈现标准,这是本项目可信度资产的一部分。
4. **产品矩阵无失控扩张**:七个形态中五个自觉压在 gate 后;两个"可用"形态(内核/harness)
   恰好是开源生态位所需的最小集。
5. **下一节点(C2+gate)的开启条件**:四种子数据齐 → C2 成文 → gate 判定报备。
   **gate 后首批事项(本评审裁定)**:①P0-1 账本外置;②支付宝上线收款闭环;③M2/M3 按 docs/08 建项。
