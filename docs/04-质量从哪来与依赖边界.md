# 04 · 追问：高质量数据从哪来？要不要依赖这三个库？

> 本文回答两个追问：①「生产高质量数据」里的质量到底从哪来；②是否应该依赖 NeMo / Data-Juicer / DataFlow。
> 第二问的答案取决于产品形态，并且会**修正 02 文档的部分结论**——02 是按「卖平台」设计的，
> 如果产品是「生产数据」本身，依赖策略要收紧。

## 1. 先修正坐标系：你到底卖什么

「生产高质量的数据」下面藏着三种完全不同的产品，依赖结论截然不同：

| 形态 | 卖什么 | 客户看到库吗 | 依赖结论 |
|---|---|---|---|
| A. 卖平台/工具 | 让别人用你的软件生产数据 | 看到（兼容生态是卖点） | 依赖合理，但只做薄适配（02 的方案） |
| B. 卖数据/数据服务 | 你自己生产数据，交付数据集或数据 API | **完全看不到** | **架构上不应依赖，库降级为内部零件** |
| C. 卖模型定制 | 数据只是中间产物 | 完全看不到 | 同 B |

如果目标是 B（「产品希望做的事情：生产高质量的数据」听起来就是 B），那么框架整合本身没有客户价值——客户只验收数据质量。**库是你车间里的机床，不是你的产品，更不该是你的地基。**

## 2. 质量的生产函数：五个环节，库只覆盖一个半

**质量不是数据的内在属性。** 操作性定义：一批数据的质量 = 训进去之后目标能力的提升幅度（per token / per dollar）。干净、去重、格式规整都只是代理指标。

质量的生产函数由五个环节相乘：

```
质量 = 源(sourcing) × 变换(transform) × 判别(discriminate) × 验证(verify) × 反馈(feedback)
```

| 环节 | 是什么 | 谁提供 |
|---|---|---|
| **源** | 选对原料：教科书级语料、真实用户日志、私域领域数据。FineWeb-Edu 的核心结论就是「小分类器选出的好源打赢更大的未过滤语料」——质量首先是**选**出来的，不是加工出来的 | 三个库都不管。**要自建（渠道+爬取+合作）** |
| **变换** | 清洗、去重、改写、合成。注意：**去重清洗是地板不是天花板**——防止质量损失，不创造质量。创造质量的变换是改写（raw web → 教科书体，Nemotron-CC 路线）与合成 | DJ、DataFlow、Curator 的主场。**商品化最严重的环节** |
| **判别** | 把质量信号编码成判别器：启发式 → 训练出的打分器（FineWeb-Edu、QuRating）→ LLM judge | 库提供一部分（打分器权重多为公开）。judge 的 prompt 与蒸馏要自建 |
| **验证** | 可验证域的硬保证：代码执行、数学答案核验、SQL 跑通、单测通过、多数投票 | **库基本不提供。当前推理数据的质量核心，必须自建** |
| **反馈** | 下游训练+评测回流，调整前四个环节的参数（阈值、配比、prompt）。质量是**迭代收敛**出来的，不是一次生产出来的 | DJ Sandbox 有原型思路，但作为产品必须自建（这是你的品控部门） |

**结论一：三个库主要覆盖「变换」和半个「判别」——恰恰是五个环节里最商品化、最可替换的部分。真正稀缺、真正构成壁垒的是源、验证器、反馈闭环，三个库都不提供。**

### 分域看质量机制（决定生产线怎么建）

**可验证域（数学、代码、SQL、工具调用、Agent 轨迹）**——优先做，因为质量可机器保证：

```
种子源 → 大规模生成(便宜模型,拼多样性) → 多级验证(执行/编译/单测/答案核验/投票)
      → 难度分层 → 去重与多样性控制 → 小代理模型训练验证 → 出厂
```

质量 = 生成多样性 × **验证器严格度**。生成是便宜的，验证器才是护城河（R1、AceMath 路线的共同点）。

**不可验证域（写作、对话、领域知识）**：质量来自更强的教师模型 + LLM judge 共识 + 人类抽检。天花板 = 教师能力，且有蒸馏合规问题（用 OpenAI/Anthropic 输出训练商用模型的条款限制）。毛利与可防御性都低于可验证域——作为补充，不作为主打。

**所有域通用**：源的质量决定上限；反馈闭环决定你能不能逼近上限。

## 3. 依赖策略：四层边界

你的直觉（"是不是不应该依赖这些库"）在 B 形态下基本正确，但"完全不依赖"会把基础设施也重写一遍，那是另一种浪费。正确的边界是分四层：

| 层 | 策略 | 内容 | 理由 |
|---|---|---|---|
| **底座** | 深依赖，放心 | Ray、vLLM/SGLang、Arrow/Parquet | 基础设施，社区巨大，不会死，无差异化价值 |
| **零件** | 浅依赖，可替换 | MinerU（PDF 解析）、Presidio（PII）、公开打分器权重（FineWeb-Edu 分类器等）、DJ 的 Ray 去重模块（BTS union-find 是真工程，自研要数月） | 单点最优工具直接用；**纪律：任何零件两周内可替换** |
| **框架** | **不依赖** | 不把流水线表达在 DJ 的 YAML 或 DataFlow 的 Pipeline 抽象上；自己的流水线表达（哪怕很薄）必须自持 | **配方是核心资产，不能写在别人的语言里**；且免于上游 API 剧变绑架（NeMo 有前科，DataFlow 在 1.0.x 快速变动） |
| **思路** | 免费，尽量学 | DataFlow 各领域流水线的阶段设计与 prompt、DJ Sandbox 的 Probe-Analyze-Refine、Nemotron-CC 改写配方、FineWeb-Edu 分类器路线 | 论文和代码全公开。学机制，自己实现关键的 20% |

一句话版本：**用它们的零件和思路，不用它们的框架；把钱花在库没有的东西上。**

### 拿来用 / 自建 / 学思路 清单

- **拿来用**：Ray、vLLM、MinerU、Presidio、fastText 语言识别、公开打分器权重、（可选）DJ Ray 去重
- **自建（差异化资产，按优先级）**：
  1. **验证器族**（每个可验证域一套：代码沙箱执行、数学核验、SQL 执行比对、轨迹回放）
  2. **评测闭环**（固定小代理模型 + 自建评测集 = 数据厂的品控部门；每批数据出厂前过一遍）
  3. **源数据管道**（领域合作、爬取、清洗到统一样本模式）
  4. **自有流水线表达 + 逐样本血缘**（很薄即可，几百行；血缘 `op_trace` 同时是审计凭证）
  5. **Judge 蒸馏产线**（LLM judge 标注 → 训小打分器 → 替换 judge，成本降一个量级）
- **学思路**：DataFlow 的 reasoning/Text2SQL/KBC 流水线结构、Sandbox 闭环方法论、各家公开数据配方论文

## 4. 对 02 方案的修正声明

- 02 的五层架构、闭环、成本漏斗、归因引擎——**方法论全部保留**（那是「怎么把数据做好」的机制，与卖什么无关）。
- 修正的是 L2「执行引擎适配器」的地位：**卖平台时它是产品的一部分；卖数据时它退化为车间内部的可替换零件层**，不对外承诺、不深度投入、随时可拆。
- 90 天 MVP（03 文档）的切片与证伪实验不变，但实现方式从「适配三个框架」改为「自持薄流水线 + 借零件」：工作量相当，可控性更高。
- 02 的「护城河在归因档案」结论**加强**了：既然变换环节是商品，护城河就更集中在验证器、评测闭环、源渠道、归因档案这四件自建资产上。

## 5. 决策树（一屏版）

```
你卖什么？
├─ 平台/工具（让别人生产数据）
│    → 依赖合理：薄适配三个库,兼容生态是卖点（按 02 执行）
├─ 数据/数据服务（自己生产数据）★ 当前方向
│    → 框架不依赖,零件可依赖,思路尽量学
│    → 预算重心：验证器 > 评测闭环 > 源渠道 > 血缘/配方表达 > judge蒸馏
│    → 先做可验证域（数学/代码/SQL/Agent轨迹）:质量可机器保证,毛利高
└─ 模型定制（数据是中间产物）
     → 同上,另加训练栈选型（NeMo 或 LLaMA-Factory 皆可,保持双栈）
```

**最终回答两个追问：**

1. **高质量从哪来**：从源的选择、可验证域的验证器、以及「训练-评测-归因」的反馈闭环里来——不从清洗算子里来。清洗去重只保住地板；验证器和闭环才决定天花板。
2. **该不该依赖那三个库**：如果产品是生产数据本身——**架构上不依赖（框架层零依赖），战术上借用（零件层白嫖其工程，思路层白嫖其论文）**。02 的整合方案只在你决定卖平台时才成立。
