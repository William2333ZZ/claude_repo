# 15 · 使用场景与保真阶梯(产品设计方法论)

> 依据委托人 2026-08-13 方法论指正:**客户使用场景须按低/中/高三级保真管理,项目按产品
> 设计方法论推进**。本文承认并修正此前的真缺陷:我们把工程做到了高保真(43 例测试、
> 公网实例、MCP 真机烟测),却让**设计锚点客户(P1)的使用场景停留在零验证**——典型的
> "先建后问"反模式。自本文起,项目推进从"技术门禁单轨"改为**技术轨 × 场景轨双轨制**。

## 1. 方法论:场景卡 → 三级保真 → 逐级验证门

每个客户使用场景(scenario)建一张**场景卡**(角色/触发/步骤/成功标准/失败信号),
然后沿三级保真阶梯推进,**每级有验证门,不过不投下一级**:

| 保真级 | 形态(对本产品) | 验证什么 | 验证手段 | 成本 |
|---|---|---|---|---|
| **低保真** | 场景叙事 + 故事板 + 一页纸访谈材料 | 问题真实存在?流程假设对? | 客户访谈(3 家起) | ≈0,数天 |
| **中保真** | 可操作原型:CLI 实录 / 试驾脚本 / demo / 控制台线框 | 交互成立?客户能自己走通? | 引导式试驾 + 脱敏样本试跑 | 低,组件多已建成 |
| **高保真** | 真实端到端:托管实例 + 客户真实数据 + 真实付费 | 价值成立?愿意付钱? | 付费 PoC(¥9,900)+ 评测对比报告 | 高,需 gate + P0-1 |

**保真的双重含义在购买旅程上重合**:对我们是"原型精度阶梯",对客户是"逐级加深的采用
路径"(读报告→试驾→拿自己数据试→付费接入)——docs/14 §3 的旅程每一步就是一次保真升级。

## 2. 核心场景卡(v1,四张)

### S1 · 私域文档变可训练数据(P1 垂直团队,设计锚点)

- **角色**:垂直模型团队算法负责人(金融/法律/医疗/制造,10–100 人,有 GPU 预算无数据基建)
- **触发**:要用私域文档(PDF/工单/合同/病历)微调领域模型,手搓清洗脚本两周仍不收敛
- **步骤(假设)**:传文档集 → 选配方(chunk→QA 合成→judge→verify→dedup)→ 看成本预估
  → 跑产线 → 读留存/死因报告 → 导出 SFT/DPO → 训练 → 评测分数回流对比
- **成功标准**:同预算下评测分 > 其自有脚本基线;每条数据可追溯(合规/审计可用)
- **失败信号**:配方迁移到其领域即失效;死因报告他们读不懂;流程假设与其真实工作流不符

### S2 · 复现配方涨点(P2 微调者/AI 应用公司)

- **角色**:开源模型微调者,拼不起数据工程
- **触发**:看到 C2 公开报告"漏斗配方在 math_zh 上稳定为正",想在自己语料上复现
- **步骤**:读报告 → `pip install` → `datafoundry demo` → 套用配方跑自己语料 → 对比
- **成功标准**:报告本身可复现(seed+sha256);其语料上方向一致
- **失败信号**:复现步骤卡壳超 30 分钟;配方在报告域之外全然无效

### S3 · Agent 驱动数据产线(横向,harness 场景)

- **角色**:用 Claude Code 的工程师(或 Agent 本身)
- **触发**:想让 Agent 自动完成"传数据→选算子→估成本→跑产线→读死因"
- **步骤**:`claude mcp add datafoundry` → 8 个 df_* 工具 → Agent 按其 API Key 角色操作
- **成功标准**:Agent 能力严格等于其 Key 对应角色;全流程无人工干预
- **失败信号**:权限旁路;Agent 需要人工救场超过 1 次/流程

### S4 · 采购与结算(支撑场景,商业闭环)

- **角色**:P1 的预算审批人 / P2 自助买家
- **触发**:试驾满意,要买额度
- **步骤**:选档 → 下单 → 支付宝扫码 → 回调核账(幂等)→ 额度到账 → run 扣减
- **成功标准**:全程无人工对账;账本可审计;失败路径(掉单/重复回调)不丢钱
- **失败信号**:任何一步需要人工介入;redeploy 后账本丢失(P0-1)

## 3. 保真现状盘点(诚实矩阵,2026-08-13)

| 场景 | 低保真 | 中保真 | 高保真 |
|---|---|---|---|
| **S1 文档→数据(锚点)** | ❌ **零访谈验证**(场景卡今日才立) | 🟡 组件全齐(#5 KBC 链/试驾/demo),但从未以"客户的文档"走通 | ❌ 需真实数据+付费,押 gate+P0-1 后 |
| S2 复现涨点 | ✅ 两种子实验叙事已档(RESULTS.md) | ✅ demo+试驾已在干净环境验证 | 🟡 等 4 种子报告发布(=首个配方包) |
| S3 Agent 产线 | ✅ docs/05 设计 | ✅ MCP 真机烟测 | ✅ 已走通,43 例测试含 MCP——全项目保真最高 |
| S4 采购结算 | ✅ docs/11/14 方案 | ✅ mock/Stripe 全测;支付宝验签链验证到 40003 | ❌ 卡支付宝提审 + P0-1 |

**矩阵读法(本次指正暴露的问题)**:S3 全绿说明"harness 优先"已兑现;但**付费意愿最强的
S1 恰恰是保真最低的场景**——工程投入与场景验证严重倒挂。纠偏动作见 §4/§5。

## 4. 双轨推进规则(并入项目管理,与 docs/08 并行生效)

1. **技术轨照旧**:WBS、北极星(gain-per-dollar)、硬门禁(#7)全部不变
2. **场景轨新增**:每场景的保真升级是产品域验收节点,入 issue 跟踪(标签 `场景:S1..S4`)
3. **低保真验证不受 gate 冻结**:访谈与场景卡零建设、零收款,不触碰任何红线——
   且**必须先行**;docs/14 §6 的 M3-H2 访谈,其低保真部分自本文起提前启动
4. **不跳级投入**:场景未过低保真验证,不为它新写代码;未过中保真,不为它做高保真承接
   ——已建成的组件不受追溯(沉没),但**新投入一律按此执行**
5. **失败即转向**:低保真验证失败(见 §5 退出标准)回 docs/03 换垂直领域,成本仅数天访谈
   ——这正是三级保真的意义:用最便宜的一级杀死错误假设

## 5. 立即行动:S1 低保真验证包(一页纸访谈材料)

> 兑现 docs/10 §4.1 的欠账。以下材料可直接用于 3 家 P1 团队访谈。

**待验假设**:
- H1:「从文档堆到可训练数据」在其痛点前三,且当前靠手搓脚本
- H2:逐条死因与血缘(合规/审计可用)是他们愿意付费的差异点
- H3:「同预算更高评测分」的叙事能换到 ¥9,900 量级的 PoC 预算

**故事板(五格,访谈时对着讲)**:
①现状:两周脚本地狱,删了什么留了什么没人说得清 → ②传文档选配方,平台给成本预估
(朴素 vs 漏斗,省 46%)→ ③跑产线,便宜算子先杀 90%,贵判审只看幸存者 → ④死因报告:
每条被删数据有死因,每条留存可追溯 → ⑤导出训练,评测分回流,和基线对比

**五个问题(开放式,不诱导)**:
1. 你们现在从原始文档到训练数据,真实流程是什么,一轮多久,谁在做?
2. 最近一次因为数据质量翻车的事,具体是什么?
3. 如果每条被删的数据都有死因、每条留下的都可追溯,这对你们值什么?(听他先说用途)
4. 「同样预算,更高评测分」——你信吗?要看到什么证据才信?
5. 花 ¥9,900 用你们的文档跑一次 PoC、出对比报告——这笔钱谁批,流程是什么?

**退出标准(低保真验证门)**:3 家访谈中 ≥2 家 H1 成立,且 ≥1 家对 H3 给出明确预算路径
→ S1 升中保真(用其脱敏样本走通产线);否则本垂直领域证伪,回 docs/03 重选。

**执行分工**(docs/09):访谈由人进行(产品域,AI 不可代理);材料、纪要模板、
纪要归档(进 docs)由 AI 执行单元承接。委托人若可引荐候选团队,列表交产品域排期。
